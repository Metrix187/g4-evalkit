# Gate runs

All runs use the 119 gold-passing dev tasks (117 gradeable after dropping 2 free-pass tasks). Phase 1 runs on Kaggle L4×4 at concurrency 12 with time scale 1.8 (5 min → 9 min wall, which gives roughly the scorer's token budget per task). Grading happens locally with the fixed grader. A missing patch counts as a fail.

## r001 (2026-10-01): thinking budget

| candidate | solved /117 | submit_patch called | hit the time limit | context overflow |
|---|---|---|---|---|
| base (think 4096) | 32 (27.4%) | 28/119 | 79 | 9 |
| **think1k** | **36 (30.8%)** | 23/89 traces | 77 | 6 |
| nothink | 25 (21.4%) | 39/119 | 78 | 2 |

Paired (discordant wins / sign test):
- think1k vs nothink: 16 vs 5, **p = 0.027**. Thinking helps.
- think1k vs base: 9 vs 5, p = 0.42. Not separated yet.
- base vs nothink: 14 vs 7, p = 0.19.

From the traces (`tools/trace_stats.py`):
- **Time is the bottleneck.** The median session ran ~500 s of its 540 s budget; about 2/3 hit the time limit.
- **Submitting is a strong signal.** For base, 82% of sessions that called `submit_patch` were solved (23/28), vs 11% of those that didn't (10/91). The model can solve these tasks; it doesn't finish in time.
- **Reading dominates.** About 7.5 `read_file` and 8 `run_command` calls per task. Graph tools are barely used (search_similar_code ~1 per task for think models, 4 for nothink; get_code_neighbors almost never), and the analyzer sub-agent was called 3-9 times across 119 tasks.
- **Junk in patches.** About half of all patches include `repro.py` / `reproduce_issue.py` written into /workspace.
- **Context overflow kills sessions.** 2-9 per candidate died with `ContextWindowExceededError` (max_output_tokens 16384 + large tool output > 32k).
- think1k produced only 89 traces for 119 tasks, all 30 missing ones are rich. Patches are complete (grading unaffected); probably a trace serialization failure on rich's terminal output.
- **Time goes to long generations, not tool calls.** In timed-out sessions, single steps that write a whole file (`write_file` of a script, `reproduce_issue.py`) took 220-270 s each: at ~20-40 tok/s, a 2k-token file costs a minute or more. Unranged `read_file` calls and 3-4k-char thoughts before edits add up too. Fix to try next: prefer small `edit_file` diffs over `write_file` rewrites, use `python -c` one-liners or existing tests instead of writing scripts, and tell the model its own generation speed.

All pairs are p ≥ 0.8. **The prompt changes moved behaviour, not outcomes.**
- fast halved `write_file` use and nearly dropped the graph tools (because the prompt said grep).
- fast_cap submits more often, but those submits are less often right: it wraps up before the fix is verified.

**Run-to-run noise:** the same think1k agent solved 31 tasks in both r001 and r002, but 6 tasks were solved only in r001 and 5 only in r002. That's 11 discordant tasks from sampling alone (temperature 0.2), so a ±5-task difference between candidates on a single run is noise.

**The gate has been starving agents** (`tools/stream_speed.py`):
- In r002, each stream ran at **~10 tok/s** (median prompt 8.3k tokens, 12 concurrent sessions). The probe's 22 tok/s was for short prompts. Tool execution is only 1-2% of session time.
- So each task got ~9 min × 10 tok/s ≈ 5.4k tokens. The scorer (single stream, ~30 tok/s with long context, 5 min) gives ~9k.
- **The gate gave ~60% of the scorer's budget**, so r001/r002 conclusions were drawn under starvation. **Use `--time-scale 3.0` from r003 on.**

**gate63:** across the 6 candidate-runs, 66 tasks were never solved, 13 always, and 38 sometimes. `notes/tasks_gate63.txt` = 38 informative + 20 never-solved + 5 always-solved (seed 1). At time scale 3.0 that's about 1.3 h of wall time per candidate.

### r003 follow-up: what "right file, wrong fix" looks like (35 task-candidate pairs, 18 tasks)

## r008 (2026-10-07): fast3, the submit_patch loop

**Why sessions loop on `submit_patch`.** The harness's baseline commit (`git commit` + tag `_swegemma_baseline`) runs with HOME pointed at the sandbox tmp dir and no git identity, so it fails, `submit_patch` falls back to `git diff HEAD`, and every patch carries the hook's `conftest.py` and `pytest.ini` as new files (65/66 in r007, 70/70 in r006b). The agent sees `files_changed: 3` after editing one file, and our own rules say not to touch `conftest.py`/`pytest.ini`, so it decides something's wrong. Its thoughts say exactly that in 12 of r007's 15 loopers ("Wait, files_changed: 3? I only edited one file"). Then it either investigates, re-submits until the 100-turn cap (7 r007 tasks ended on "exceeded turns budget"), or rambles for one long generation (jinja_1664: one 415 s call after its only submit). In r007, 13% of agent time came after the first submit; fast2 runs show 5-11% and 12-14 loopers per block. The grade itself is fine: verification resets both files and the patch still applies. It's pure time, and on the sequential scorer that time counts against the 12 h limit.

fast3 = fast2_spec plus one step: "6. Stop. `submit_patch` doesn't end the session; a reply without a tool call does. ... Its `files_changed` can include `conftest.py` and `pytest.ini`: the harness added those ..., and they're dropped at grading." Worded so it stays true if the scorer's baseline commit works.

Pushed 10:21 UTC Oct 7 (`g4-gate` v8) with the quota that would expire Oct 10 anyway: fast3 on `notes/tasks_meval_loopers12.txt`, the 12 r007 tasks with the most post-submit time (4/12 resolved in r007). One round at concurrency 12, ~1.2 quota-h. It's a mechanism check (loops gone, nothing worse), not a score comparison. r008 ran that first cut (sha 460d7cb1, stop rule only).

**Second fix, added to fast3 after r008 was pushed:** step 4 told the agent "if you really need a file, put it in /tmp", but `write_file`/`read_file`/`edit_file` refuse any path outside the workspace (`_resolve_workspace_path`: "Path traversal detected"). That cost a tool call plus a whole script's worth of tokens in 20/66 r007 sessions (15/66 in r005, 27/70 in r006b; every FileWriteError we logged is this one). fast3 now says don't create scratch files at all.

**r008 result (12 looper tasks, graded locally; 19.5 kernel min, all 12 in one round):** the loop is gone. `submit_patch` calls on these 12 tasks went from 771 (r007) to 13, and every session ended with "Agent finished" seconds after its last submit; no turn-budget errors. But resolution was 2/12 (r007 4/12), and 6/12 final patches were empty, harness files only, against 1-3 for every earlier run on the same tasks (fast2 1, lora 2, t1 2, lora2 3, fast2_spec 1). jinja_1495, which all five earlier runs solved, ran out of calls (first edit was call 25, after a /tmp FileWriteError that the newer cut removes). packaging_1346/1163/939 lost 13-14 turns each to malformed `edit_file` calls ("mandatory input parameters are not present: old_string"), a per-task glitch fast2_t1 and fast2_spec also show. These 12 tasks were picked for r007's post-submit time, which means r007 had landed a real edit on 11 of them, so some regression to the mean is expected. Read it as noise plus a yellow flag: fast3 needs both full blocks after the Oct 10 reset before it can be a final pick.

**r009** (`g4-gate` v9, pushed 10:54 UTC Oct 7): the current fast3 (stop rule + no /tmp, sha dbbbae7d) on the same 12 tasks, to see whether r008's 2/12 and six empty patches come back. Uses most of the ~1.3 quota-h left before the reset.
